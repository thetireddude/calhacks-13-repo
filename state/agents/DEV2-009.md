### P2

1. **In-memory confirmation vs true concurrency**
   - **Area:** `apps/api/src/voting/store.ts` (`tryConfirmFromMajority`)
   - **Issue:** Double-check before `Map.set` is not atomic across concurrent HTTP handlers that `await` in `requireAuth`; two approvals could theoretically interleave and leave the last writer’s `proposalId`/`id` as the stored confirmation (still one row/key per group).
   - **Why it matters:** SPEC and AGENTS.md require idempotent confirmation under concurrent votes; the DB layer’s `unique (group_id)` will enforce at most one row when wired; in-memory stub is weaker until a transactional upsert (e.g. `INSERT … ON CONFLICT DO NOTHING`) lands.
   - **Smallest fix:** Defer to Supabase wiring task; optional per-group mutex or single-flight wrapper if in-memory must mirror production concurrency in CI.

2. **In-memory voting vs migration**
   - **Area:** `InMemoryVotingStore`, default in `createApp()`
   - **Issue:** Routes do not read/write `proposal_votes`, `proposal_vetoes`, or `confirmed_events` yet.
   - **Why it matters:** Expected Gate 1 stub (same pattern as planning/prefs); restart loses votes until persistence task.
   - **Smallest fix:** Track explicit Dev 2 wiring task; no change required for this slice.

3. **RLS: member-visible vote rows at persistence layer**
   - **Area:** `20261024180300_votes_confirmed_events.sql` (`proposal_votes_select_member`)
   - **Issue:** Any group member with PostgREST access can `SELECT` all rows for a proposal, including other members’ `cant_make_it` choices. HTTP API today returns only the caller’s vote on `PUT`, not a list endpoint.
   - **Why it matters:** Product may later restrict whether absence reasons are group-visible; not a leak of prefs/availability, but visibility of vote choice is broader at SQL than current REST surface.
   - **Smallest fix:** When wiring API to Supabase, use service-role aggregation or narrow policies if SPEC/ADR requires hiding `cant_make_it` attribution.

4. **`confirmed_events` writes service-role only**
   - **Area:** migration RLS (SELECT for members; no member INSERT)
   - **Issue:** Confirmation inserts must use backend service role (consistent with proposals write pattern in DEV2-007).
   - **Why it matters:** Correct for “backend owns confirmation”; document in wiring task.
   - **Smallest fix:** Comment in migration or wiring task checklist.

5. **Stub consensus ignores vetoes**
   - **Area:** `tryConfirmFromMajority`, vote route
   - **Issue:** Majority uses approve count only; vetoes do not block confirmation.
   - **Why it matters:** Matches task (“simple majority of members on `approve` until SPEC §11”); must not be mistaken for final product rules.
   - **Smallest fix:** None for this task; revisit when SPEC §11 veto/revote behavior is approved.

6. **Task / state files in commit**
